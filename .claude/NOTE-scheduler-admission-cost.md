# 記録: 受け入れられない要求が、周回ごとに何をしているか

**これは仮説ではなく、機構の記録である。**
発端は「待機要求が居ると decode が 11% 遅い」という観測だったが、
**その観測は取り下げた**（下記）。残す価値があるのは機構の方だけ。

---

## 取り下げたもの

`#queue-req=1` の decode 行が `q=0` より 11% 遅い、という観測を出した。**取り下げる。**

`q=1` の 77 行のうち 58 行が 01:12 の1分に集中し、**その時間帯に `q=0` の行が1つも無い。**
同時刻の対照が存在しない。除くと差は 5%、標本 19 行。
そして後述のとおり、機構から見込める効果は **1% 程度**で、
要求間の散らばり（四分位 70.1–84.3 tok/s、±9%）の下に埋まる。

**説明すべき効果がデータに無い。** A/B/C の弁別実験も不要（上限が既に分かっているため）。

---

## 機構（コードから確定。これは残す）

待機要求は毎周回、受け入れを試される。`prefill.py:328`:

```python
for pending_req in self.pending_list:
    if req := adder.try_add_one(pending_req):     # -> _try_allocate_one (prefill.py:76)
```

`_try_allocate_one` は**サイズ検査より先に** `match_req` を呼ぶ。中で走るのは:

| 段 | 実体 | どこで | 備考 |
|---|---|---|---|
| `_walk` | `fast_compare_key`（C++、*"compare 2 1-D int **cpu** tensors"*） | **CPU** | Python ループではない |
| `split_at`（部分一致時） | 木を分割し `node.timestamp` を更新 | CPU | **木と LRU を変形する** |
| `_collect_kv` | `torch.cat(vals)` 最大10万 int32 | **GPU** | `page_table` は `device=self.device`（`engine.py:458`）。**生きたスナップショットに当たった時だけ通る** |

そのあと `estimated_size + reserved_size > available_size` で弾かれ、**全部捨てられる。**

**要するに: 待機要求1本につき、forward ごとに match が1回走って捨てられる。**

### 費用

**1回あたり 0.05〜0.19 ms**（査読者の実測。**私はこの数字を再現していない**）。

80 tok/s なら 1 forward が約 12.5 ms なので、**0.4〜1.5%**。
要求間の散らばり（±9%）に埋まる。**本番ログでは測れない。**

### 在置きの修正との関係

`_collect_kv` は**生きたスナップショットに当たった時だけ**通る。
修正前の実トラフィックは `snap_trunc=0` が 98% で、`self.empty` を返して cat は起きていなかった。
**修正後は一致するので cat が走るようになる。**

ただし上の上限（1 forward の 1.5% 以下）は変わらない。
**prefill 側の利得（792 → 119 秒、`5b862bd`）と比べる規模ではない。既定の反転を止める理由にならない。**

### 費用ではない側面（未測定）

`split_at` は、**一度も実行されない要求のために**木を分割し `node.timestamp` を更新する。
これは時間ではなく**追い出し順**に効く。待ち行列が深いとき、
走らない要求が LRU を触り続けることになる。**測っていない。別の観測が要る。**

## この件で decode 側に問題があるとは言っていない

実 decode は文脈 120k でも 76.8 tok/s、20–40k の 86.2 から 11% 落ちるだけ
（MT の実セッション、841 行）。**ここ自体は壊れていない。**
