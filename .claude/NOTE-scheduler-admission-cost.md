# 記録: 受け入れられない要求が、周回ごとに何をしているか

**これは仮説ではなく、機構の記録である。**
発端は「待機要求が居ると decode が 11% 遅い」という観測だったが、**その観測は取り下げた**。
残す価値があるのは機構の方だけ。第2版（査読を反映）。

---

## 取り下げたもの ——「待機要求が decode を 11% 遅くする」

**根拠は4つあり、どれ単独でも取り下げに足りる。**

**1. 要求単位で見ると差が消える。** `#running-req=1`、文脈 100k–140k の連続区間（5行以上）で:

```
q=0 の区間中央値: 87.2  68.8  77.8  83.0  71.5  77.7  79.3  75.4  70.2  （9区間）
q=1 の 01:12    : 67.6
その直後 01:13:00、同じ 110k 帯を q=0 で: 71.5
```

**条件内の散らばり（68.8–87.2）が、条件間の差を飲み込んでいる。**
同じ要求が待機ありで 67.6、直後に待機なしで 71.5。行数で数えれば差が出るが、区間で数えれば出ない。

**2. 機構から見込める効果は 1% 程度**（後述、0.19 ms / 14.9 ms = 1.3%）で、
要求間の散らばり（±9%）の下に埋まる。**本番ログでは原理的に測れない。**

**3. 観測の時間帯に `_collect_kv` は走っていない。** 01:12 の walk 行 **2,340 本すべてが `snap_trunc=0`**。
`torch.cat` は観測の説明になり得ない。

**4. 同時刻の対照が無い。** `q=1` の 77 行中 58 行が 01:12 の1分に集中し、
その分に `q=0` の行が1つも無い。

**説明すべき効果がデータに無い。** 弁別実験（A/B/C）も不要 —— 上限が既に分かっている。

---

## 機構（コードから確定。これは残す）

待機要求は毎周回、受け入れを試される。`prefill.py:328`:

```python
for pending_req in self.pending_list:
    if req := adder.try_add_one(pending_req):     # -> _try_allocate_one (prefill.py:76)
```

`_try_allocate_one` は `match_req` を**サイズ検査より先に**呼ぶ。
**ただし例外がひとつ** —— `available_size == 0` なら match の前に戻る（`prefill.py:77`）。

| 段 | 実体 | どこで |
|---|---|---|
| `_walk` | **Python のループ**（`hybrid_radix_cache.py:293-310`）。ノードごとに dict 検索、`key_fn`＝`lambda x: x[0].item()`（`radix_cache.py:264`）、時刻の書き込み | CPU |
| ├ ノード内の比較 | `fast_compare_key`（C++、*"compare 2 1-D int cpu tensors"*） | CPU |
| `_collect_kv` | `torch.cat(vals)`。**生きたスナップショットに当たった時だけ**通る | GPU |

そのあと `estimated_size + reserved_size > available_size` で弾かれ、**全部捨てられる。**

**要するに: 待機要求1本につき、forward ごとに match が1回走って捨てられる。**

これはコードからの推論だが、**実証もある** —— 01:12 の walk 行は**毎秒 67 本**で、
そのときの decode 67–68 tok/s と一致する。1周回 = 1 forward = 1 match。

### 費用（実測。ノード数に比例する）

道具 `freetoken-systest/tools/{radix-match-cost-bench.py,radix-snapshot-hit-cost-bench.py}`（`3f339ea`）、
一次出力 `freetoken-systest/results/20260907T033226-diag_queue-match-cost.txt`。
モデル不要、10 秒ほどで回る。以下は `FREETOKEN_PREFIX_DEBUG=1`（観測時と同条件）の値。

```
経路ノード  7、snap 無し（観測どおりの形）   中央値 0.048 ms
経路ノード 60、snap 無し                     中央値 0.186 ms
経路ノード 61、生存 snap に当たる（修正後）  中央値 0.190 ms   ← 同期なし＝スケジューラの実費用
```

**費用は CPU 側で、ノード数に比例する。** `torch.cat` の GPU 実行は **8.5 µs**（60塊・0.43 MB、CUDA event 計測）、
CPU 発行費用も 0.008 ms。GPU が別ストリームで忙しくても 0.186 ms で変わらない。

**同期込みで出る 2.3 ms は空いた GPU の起床待ちであり、引用しない。**

decode 1 ステップは 67 tok/s で約 14.9 ms。**0.19 / 14.9 = 1.3%。**

### 在置きの修正との関係

`_collect_kv` は生きたスナップショットに当たった時だけ通る。
修正前の実トラフィックは `snap_trunc=0` が 98%（FINDINGS 291 行）で、cat は起きていなかった。
**修正後は一致するので cat が走るようになる。**

ただし増分は 0.186 → 0.190 ms、**forward の 1.3%**。
**prefill 側の利得（792 → 119 秒、`5b862bd`）と比べる規模ではない。既定の反転を止める理由にならない。**

### 費用ではない側面（未測定）

`node.timestamp` を更新するのは `split_at` ではなく **`_walk` が通った全ノード**
（`hybrid_radix_cache.py:306, 308`）。また split は初回だけで、以後の周回は初回に作った境界に
ちょうど当たる —— 01:12 の walk 行 2,340 本はすべて `tok_match=21680` の1種で、再分割は起きていない。

正しくは: **走らない要求が、一致した経路の時刻を forward ごとに MRU に戻し続ける。**
触るのは皆が共有する先頭経路なので**追い出し順への実害はたぶん無い**が、**測っていない。**

### 待機要求が待っていたもの（プレフィックスキャッシュ側の話）

`token usage` 0.41 で、109k の文脈2本ぶんと出力予約がプールに入らなかった。
走っていた方が終わってから、`#cached-token: 0` で **23 秒の全量 prefill**。
**これは待ち行列の費用ではなく、プレフィックスキャッシュが効いていないことの帰結である。**

## この件で decode 側に問題があるとは言っていない

MT の実セッション（Decode 841 行、`#running-req` は問わない）:

```
文脈  20k– 40k   68 行   86.2 tok/s
文脈 110k–130k  157 行   76.8 tok/s
文脈 120k–140k  256 行   76.8 tok/s
```

**文脈が5倍になって 11% 落ちるだけ。ここ自体は壊れていない。**
