# 仮説: 待機している要求が decode を遅くしているか

評価してもらうための文書。**まだ何も主張していない。**
とくに **観測そのものが確立していない**（下記「観測の限界」）。
すべてこの箱（RTX 4090 24GB）、MT の実セッション 2026-09-07 01:01–01:19 のログから。

---

## 説明したい観測

`#running-req=1`、文脈 100k–140k に揃えた decode 行:

```
#queue-req=0   355 行   中央値 77.1 tok/s   （四分位 70.1–84.3）
#queue-req=1    77 行   中央値 68.4 tok/s   （四分位 65.2–72.6）
```

**待っているだけの要求が1本あると、ログ上の decode が約11%遅い。**

平凡な説明は2つとも当たらなかった。

* **待機要求の prefill が時間を取っている** —— 違う。近傍 ±2 / ±5 / ±10 / ±30 行の
  どの窓でも、`q=1` の 77 行は prefill 行を伴わない（±30 でも 76/77）
* **資源の逼迫** —— 違う。`token usage` は `q=1` の方が**低い**（0.42 対 0.46）、
  `mamba-slot` は両群とも中央値 4

### 観測の限界（ここが一番大事）

**対照が取れていない。** `q=1` の 77 行のうち **58 行が 01:12 の1分に集中**し、
**その時間帯に `q=0` の行が1つも無い。**

```
01:12       q=0   0 行        q=1  58 行  中央値 67.6
01:12 以外  q=0 355 行 77.1   q=1  19 行  中央値 73.5   （差 5%、標本 19）
```

その1分を除くと差は 5%、標本 19 行。**11% という数字は1つのエピソードが作っている。**
この差が待ち行列のせいなのか、その時間帯のせいなのか、**このログからは分けられない。**

## 機構（コードから確定していること。仮説ではない）

待機要求は毎周回、受け入れを試される。`prefill.py:328`:

```python
for pending_req in self.pending_list:
    if req := adder.try_add_one(pending_req):     # -> _try_allocate_one (prefill.py:76)
```

`_try_allocate_one` は**サイズ検査より先に** `match_req` を呼ぶ。その中で:

| 段 | 実体 | どこで走るか |
|---|---|---|
| `_walk` | `fast_compare_key`（C++、"compare 2 1-D int **cpu** tensors"） | **CPU** |
| `split_at`（部分一致のとき） | 木を分割し `node.timestamp` を更新 | CPU（**木と LRU を変形する**） |
| `_collect_kv`（**生きたスナップショットに当たった時だけ**） | `torch.cat(vals)`、最大10万要素 | **GPU**（`page_table` は `device=self.device`、`engine.py:458`） |

そのあと `estimated_size + reserved_size > available_size` で弾かれ、**全部捨てられる。**

## 仮説

**H0 — 帰無・共起。** 待ち行列は原因ではなく目印。1分に固まったエピソードの何か
（クライアント側の負荷、ホストの競合、offload のページング、熱）が両方を起こしている。
**現データはこれを排除できていない。第一候補として扱う。**

**H1a — `_walk` と `split_at` の CPU 費用。**
10万要素の memcmp はマイクロ秒。**機構を読んだ時点で弱い。**
ただし `split_at` は木と LRU 時刻を**変形する**ので、費用ではなく
**後続の追い出し順を狂わせる**副作用の方が問題になりうる（別の観測が要る）。

**H1b — `_collect_kv` の `torch.cat` が GPU を取る。**
待機要求1本につき毎周回、最大10万 int32（約400KB）の device コピーとカーネル起動が、
decode と同じデバイスで走る。**機構としては最も有力。**

**H2 — 指標の作り物。** ログの `gen throughput` は動くが実速度は変わっていない。
上流 #306（*client wall-clock is ~half the scheduler gen throughput*）と同じ形。

**H3 — GDN スロット競合。既に否定済み**（`mamba-slot` 両群とも中央値 4）。

---

## ここから出る予測（在置きの修正に関わる）

**修正は、この費用を増やす方向に働く可能性がある。**

`_collect_kv` は**生きたスナップショットに当たった時だけ**通る。
修正前の実トラフィックは `snap_trunc=0` が 98% で、`self.empty` を返して cat は起きていなかった。
**修正後は一致するので、待機要求1本につき毎周回 cat が走る。**

H1b が正しければ、**既定を反転する前に知っておくべき副作用**である。
反転を止める理由になるとは限らない（prefill 側の 6.6 倍と比べる話）。

## 弁別実験

待機要求は「KV プールより長い要求」で作る（上流 #111: *queued forever with no error*）。
プール は `--kv-reserve-tokens 262144`。

| 条件 | 内容 |
|---|---|
| **A** | 長い要求を1本だけ decode させる。待機なし |
| **B** | A に加え、**一致しない**プロンプトの受け入れ不能要求を1本キューに積む |
| **C** | A に加え、**長く一致する**（生きたスナップショットに当たる）受け入れ不能要求を1本積む |

**ログの `gen throughput` とクライアント側のトークン間遅延を両方測る。**

| | A | B | C |
|---|---|---|---|
| H0 | = | = | = |
| H1a | = | 落ちる | もっと落ちる |
| H1b | = | = | **落ちる** |
| H2 | ログだけ動き、クライアント側は変わらない |

**B と C の差が H1b を分離する。** B は `_walk` だけ、C は `_walk` + `torch.cat`。

---

## この実験が壊れうる点（先に書いておく）

* **受け入れ不能要求が本当にキューに留まるか。** 長さで弾かれてエラーになるなら条件が作れない。
  上流 #111 の記述に頼っているが、**この箱で確認していない。まず単体で確かめる**
* **C の「長く一致する」を作れるか。** 木の状態に依存するので、
  decode 中の要求と同じ前置きを持たせる必要がある。`FREETOKEN_PREFIX_DEBUG=1` の
  `walk tok_match=` で、狙いどおり一致したかを毎回確認する
* **キューに積んだ要求が途中で受け入れられてしまう**と条件が崩れる。`#queue-req` を毎行確認する
* **A/B/C を同一プロセスで連続実行すると木が育つ**。冷↔冷で分ける
* **効果量が小さい可能性。** 11% は1エピソードの数字で、真値は 5% 以下かもしれない。
  その場合は反復回数を増やさないと有意にならない。**先に何回必要かを決めてから回す**

---

## 主張していないこと

* **decode に問題があるとは言っていない。** 実 decode は文脈 120k でも 76.8 tok/s、
  20–40k の 86.2 から 11% 落ちるだけで、ここ自体は壊れていない
* **H1b が正しいとも言っていない。** 機構として最有力というだけで、測っていない
* **11% という数字を成果として出さない。** 対照が無い
